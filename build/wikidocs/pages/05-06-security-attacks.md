[[TIP("🟢 한눈에 보기")]]
Bluetooth 공격은 크게 두 부류입니다.

1. **규격 설계의 빈틈**을 노린 공격 — 규격대로 만든 모든 기기가 영향을 받습니다. 대응은 규격 정오표와 새 기능(최소 키 길이, 상호 인증 명확화 등)입니다. KNOB, BIAS, BLURtooth, BLUFFS가 여기에 속합니다.
2. **구현 버그**를 노린 공격 — 특정 칩·스택의 메모리 오류, 상태 기계 오류입니다. 대응은 펌웨어 패치와 퍼징입니다. BrakTooth가 대표적입니다.

공통 교훈은 **"협상 가능한 것은 다운그레이드 대상"**이라는 점입니다. 키 길이, 페어링 방식, 인증 방향처럼 양쪽이 합의하는 값을 공격자가 약한 쪽으로 끌어내립니다. 이 페이지는 공격 원리와 대응만 다루며 재현 방법은 다루지 않습니다.
[[/TIP]]

## 원인과 대응 (🔵 중급)

| 공격 | 원인 | 규격 대응 | 구현·운용 대응 |
|---|---|---|---|
| 무효 곡선 | 수신한 공개 키가 곡선 위의 점인지 검증하지 않음 → 공유 비밀이 작은 집합으로 떨어짐 | 공개 키 검증을 명시적 의무로 | 공개 키 전체 좌표 검증, 펌웨어 업데이트 |
| KNOB | BR/EDR 키 길이(1–16옥텟)를 **인증·무결성 없이** LMP로 협상 → 1옥텟 키로 다운그레이드 | 정오표: BR/EDR 최소 키 길이 **7옥텟**; 5.3 `HCI_Set_Min_Encryption_Key_Size` | 호스트가 키 길이 확인 후 짧으면 연결 거부(가능하면 16옥텟 요구) |
| BIAS | 레거시 인증이 단방향, 역할 전환으로 공격자가 검증자가 됨, SC로 본딩된 상대와도 레거시 인증으로 다운그레이드 가능 | 정오표: 상호 인증을 호스트 책임으로 명확화 | 상호 인증 강제, SC로 본딩한 상대의 레거시 다운그레이드 거부, **Secure Connections Only** 모드 |
| BLESA | 재연결 때 인증·암호화가 선택 사항처럼 처리되거나 실패 시 평문으로 계속 진행 | — | 본딩된 상대와 재연결하면 암호화 성공 전까지 보호된 데이터 처리 금지 |
| BLURtooth | CTKD가 한 전송의 페어링 결과로 다른 전송의 **기존(더 강한) 키를 덮어씀** | 5.1부터 특정 상황의 키 덮어쓰기 제한 | 약한 키로 덮어쓰기 거부, CTKD 시 사용자 확인, 불필요하면 CTKD 끄기 |
| BrakTooth | LMP·기저대역 처리의 길이 검사 누락, 비정상 순서 PDU 처리 오류 → 서비스 거부, 일부 칩에서 코드 실행 | — (규격 위반 구현) | 칩 공급사 펌웨어 패치, 프로토콜 퍼징 |
| BLUFFS | 세션 키 유도에 양쪽이 낸 값이 신선하게 섞이지 않아, 약한 세션 키를 여러 세션에서 재사용시킬 수 있음 | SIG 권고: 7옥텟 미만 키의 서비스 연결 거부 | Secure Connections Only 모드, 레거시 페어링 대신 SC 사용 |

[[TIP("🔴 전문가 노트 — 공격별 세부와 실무 체크")]]
**KNOB의 핵심.** 키 길이 협상 PDU(`LMP_encryption_key_size_req`)는 암호화 시작 전에 평문으로 오가며, 협상 결과는 호스트에 기본적으로 보고되지 않았습니다. 그래서 호스트가 정상 동작을 해도 1바이트 키로 암호화된 링크를 알아채지 못했습니다. LE는 SMP에서 호스트가 직접 7–16옥텟으로 협상하므로 최종 키 길이를 호스트가 알고 정책으로 거부할 수 있습니다. 후속 연구에서 LE에서도 짧은 키(7옥텟) 수락 정책이 위험하다는 점이 지적되었으므로, 16옥텟 요구가 권장됩니다.

**BIAS의 세 요소.** ① 레거시 인증은 한쪽(검증자)만 상대를 확인, ② 기저대역 페이징 이후 언제든 역할 전환 가능, ③ SC로 본딩한 상대라도 연결 수립 때 레거시 인증으로 떨어질 수 있음. 공격자는 본딩 키를 모른 채 "인증하는 쪽" 역할만 맡아 사칭합니다. Secure Connections Only 모드 기기는 영향을 받지 않습니다.

**BLURtooth의 범위.** 연구진은 CTKD가 도입된 4.2 이후 CTKD를 지원하는 기기 전반이 대상이라고 보았고, 5.1·5.2 기기에서도 재현했다고 밝혔습니다. 즉 "5.1이면 안전"이 아니라 5.1의 제한을 **구현이 실제로 적용했는지**가 중요합니다.

**BrakTooth 규모.** 2021년 8월 31일 공개 당시 11개 공급사의 13개 BR/EDR 칩을 조사해 16개 취약점을 보고했고 20개 CVE가 배정되었습니다(일부 공급사 CVE는 공개 시점에 대기 중). 공급사마다 패치 여부가 달라 제품 단위 확인이 필요합니다.

**실무 체크리스트.** ① 새 제품은 LE SC / BR/EDR SC만 허용, ② 키 길이 16옥텟 요구(최소 7옥텟 미만은 무조건 거부), ③ 본딩된 상대와는 암호화 성공 전 민감 데이터 처리 금지, ④ CTKD 결과가 기존 키보다 약하면 거부, ⑤ 칩 펌웨어 보안 공지 추적.
[[/TIP]]

## Classic ↔ LE 비교

| 항목 | Classic (BR/EDR) | LE |
|---|---|---|
| 키 길이 협상 | 컨트롤러(LMP), 원래 1옥텟까지 | 호스트(SMP), 7옥텟 이상 |
| 인증 다운그레이드 | 레거시 E1 인증(BIAS) | Legacy Pairing(도청), BLESA |
| 대표 구현 공격 | BrakTooth | 무효 곡선 등 SMP 구현 오류 |
| 최선의 방어 | Secure Connections Only 모드 | Secure Connections Only 모드 (Mode 1 Level 4) |
